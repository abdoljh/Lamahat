### Three new bugs found — from watching the actual output, not logs (P7.7)

Screenshots caught what audit-log analysis structurally cannot: what the
audience actually sees. All three root-caused against this run's real
`shot_plan.json` (84 shots, 80 caption events) and reproduced pixel-for-
pixel with a direct `ffmpeg`+`libass`+Amiri render — not inferred.

1. **Title card text leaking into the next shot's caption.** Event 0
   spanned the title card (hidden, 0.13–4.13s) AND the opening narration
   sentence; `_write_captions` correctly computed the VISIBLE time span
   after clipping but then burned the event's FULL text regardless —
   so shot 2's caption showed "مذكرات جعفر العسكري" (the title, spoken
   during the hidden portion) glued onto the real caption. Root cause:
   `CaptionEvent` only carried aggregate start/end/text, no word-level
   timing, so a clipped sub-span had no way to reconstruct partial text.
   Fixed: `CaptionEvent.words` (word, start, end) triples; a clipped
   span now burns only the words whose timing falls inside it.

2. **Whole clauses silently vanishing.** "وترك لنا سجلا دقيقا عن حقبة لم
   يعرفها سوى من عاشوها بكل تفاصيلها" never appeared at all. Cause: the
   sentence's tail fell entirely within a `broll` shot the planner had
   marked `show_caption=False`, immediately followed by a `typography`
   shot (inherently hidden) — the two hidden ranges were contiguous, so
   the ENTIRE remaining span of that sentence clipped to nothing.
   `show_caption=False`'s old semantics (from the per-shot caption
   system) meant "this shot's own self-contained caption is redundant" —
   in the sentence-track system that same flag on a real-image shot now
   silently deletes narration. Fixed: events-mode hidden ranges come
   ONLY from `TYPOGRAPHY_VISUALS` shots; `show_caption` on image-kind
   shots no longer affects the sentence track.

3. **Trailing Arabic comma renders at the wrong end of the line.** A
   caption ending "...وطنه،" burned as "،...وطنه" — the comma visually
   escaping to the START of the RTL line instead of trailing it.
   Reproduced directly (isolated from this codebase) with `ffmpeg`+
   `libass`+Amiri: any caption text or wrapped line ending in ، ؛ or ؟
   with nothing after it exhibits this — a known libass/fribidi neutral-
   character bidi resolution gap when a trailing mark has no following
   strong character to anchor it. Confirmed NOT digit-related (`سنة
   ١٩٠١،` and bare `وطنه،` show the identical bug) and confirmed
   per-visual-line (the first line of a `\N`-wrapped two-line caption
   needs its own fix, independent of the whole Dialogue field's true
   end). Fix verified empirically across 5 candidate approaches — only
   an invisible RLM (U+200F) appended immediately after the trailing
   mark anchors it correctly; `_wrap_caption` now applies this to each
   visual line independently via `_anchor_trailing_punct`.

All three verified end-to-end: real `shot_plan_v3.json` word timings run
through the fixed `_write_captions`, then actually burned to pixels via
`ffmpeg`+`libass` — not just ASS-text inspection. This bug class exists
BECAUSE the sentence-track shipped in P7.2 (a per-shot caption system
never had cross-shot text or cross-shot hidden-range clipping to get
wrong) — screening real output past the log-analysis stage is what
caught it.

Pure local recomputation: no Claude API call, no re-fetch, shots/images

existing dossier, then re-render-only at zero extra API cost:


## P7.8 (2026-07-29) — why the repair changed nothing: two shot_plan.json copies

User ran `regenerate_captions.py` in the render-only notebook, it
reported success (`wrote output/review/shot_plan.json`), and the next
render was **identical** — same title leak, same "الحركة القومية
العربية" repetition. They also noticed `shot_plan.json` and
`word_timings.json` "appear in more than one location".

That observation *is* the bug. The render-only notebook sets
`PLAN_FILE = "output/shot_plan.json"` and `REVIEW_DIR = "output/review/"`,
and the render log's own header confirms which one it read:

```
Plan   : output/shot_plan.json  (84 shots, 80 sentence captions)
Review : output/review/ (dossier consulted before fetcher)
```

The script patched `output/review/shot_plan.json`; the renderer read
`output/shot_plan.json`. Two files, one patched, the wrong one used —
so a perfectly working fix produced a byte-identical film.

**Durable fix — the renderer now self-heals, so the copy question stops
mattering.** `plan.repair_caption_events()` runs at load time in both
render entry points (`render_plan.py`, `render_from_review`): when a
plan's caption events carry no `words`, it finds a `word_timings.json`
beside the plan or in the dossier and attaches per-word timing to each
event. Conservative — an event is only repaired when the words inside
its own time range join back to EXACTLY its stored text, so a mismatched
narration leaves it untouched rather than burning something never said.
Verified on the real stale plan: 80/80 events repaired, all passing the
text-identity check.

`regenerate_captions.py` now also repairs **every** `shot_plan.json` it
finds (review dir *and* its parent) and prints each path, so running it
by hand can't miss a copy either.

## P7.9 (2026-07-29) — the real root cause: cards are not on their own words

User, after the P7.8 render: *"The latest version only fixed part of the
current issues! It seems clearly that the source of these issues is
inaccurate synchronization."* Their evidence, straight from the plan:

```
shot 1  typography_text: "مذكرات جعفر العسكري"
        caption_text   : "مذكرات جعفر العسكري رجل واحد حمل"
shot 3  typography_text: "أشرس الأعداء قد يكونون من داخل صفوفك."
        caption_text   : "لكنه اكتشف أن أشرس الأعداء قد يكونون من داخل صفوفك"
```

They are right, and it is the root cause — everything before this was
symptom management. Measured across that plan's 33 typography cards, by
locating each card's text in the narration word timings:

| | |
|---|---|
| cards within 0.5 s of the words they quote | **4 / 33** |
| median drift (card in/out vs its own words) | **3.10 s** |
| worst | card up **10.0 s before** its words, gone 12.3 s before they end |

A card also suppresses the subtitle track. So a drifted card shows
sentence A in silence while the narrator speaks sentence B: the viewer
reads one thing, hears another, and gets no subtitle for either. Both
of the user's reported symptoms fall out of this directly — shot 1's
card covers only the first 3 words of a 6-word span, so "رجل واحد حمل"
went uncaptioned and the caption resumed mid-phrase.

**`plan.sync_typography_to_speech()`** repairs each card, choosing per
card between two bounded edits:

* **trim** (8 cards) — the card's words are inside its own shot, so the
  shot tightens onto them and the freed time goes to the *immediate*
  neighbour, if that neighbour has room under `HARD_CAPS`.
* **retext** (20 cards) — the card quotes something spoken elsewhere, so
  the card is rewritten to the words actually spoken under it. It loses
  the planner's editorial trim and gains the only thing that matters: it
  says what the audience is hearing.

A first attempt reflowed the whole timeline to place every card exactly.
It scored better on paper (27/31 cards within 0.5 s) but pushed **13
image shots past their duration caps** — reintroducing the static-hold
problem this project spent P7.4 fixing. Rejected in favour of the local
version, which touches only neighbours.

| | before | after |
|---|---|---|
| card says what is heard (token IoU, median) | 0.50 | **1.00** |
| cards at ≥0.8 agreement | 5/33 | **30/33** |
| shots / over-cap shots | 84 / 0 | 84 / **0** |
| longest shot | 7.87 s | 7.87 s |

Shot count, order and contiguity are preserved, so a dossier keyed by
shot index stays valid — this runs on an existing dossier with no
re-plan and no API cost. Wired into `build_shot_plan` (after
`_validate_plan`, before `_fill_captions`) and into
`regenerate_captions.py` (`--no-sync-cards` opts out).

The opening, burned to pixels, before and after the whole P7.7–P7.9 arc:

## P7.9 second correction (2026-07-30) — uncovering was too eager, caused duplicate text

User re-screened a fresh 0:00–5:00 render-only cut against the three
fixes above and reported "2 and 3 are fine but not 1" (the
`card_hides_captions` fix). Confirmed on screen, not guessed: at 0:55
(shot 12, section_mark `من الموصل إلى الاستانة — رحلة التحديث
والطموح`) the caption underneath read `من الموصل إلى الاستانة رحلة
التحديث والطموح` — the same sentence, once large as the card, once
small as the caption, at the same time. Same at 0:28 (shot 7).

Root cause: `_locate_card`'s match for these two cards **does** fall
mostly inside their own shot — they missed the strict trim window
(which requires BOTH ends within `tolerance=0.35s`) only because the
sentence runs a couple of seconds into a neighbouring shot. Measured
coverage (fraction of the located quote's words actually spoken inside
the card's own on-screen span): shot 7 = 0.64, shot 12 = 0.57. My
Case 2 treated "missed the trim window" as equivalent to "displaced
elsewhere" and uncovered both — putting a near-duplicate of the card's
own words on screen as the caption. Shot 16, the case that DID look
right to the user, has coverage 0.00 — its caption shows a genuinely
different, complementary sentence, which is why side-by-side reads
fine there.

Fix: `sync_typography_to_speech` now computes this coverage and only
uncovers when it is **< 0.5** — a card whose quote is mostly inside its
own span stays hidden even though it missed the trim window, since a
slightly early/late caption is a smaller sin than showing the same
sentence twice at once. Re-run on the reference plan: uncovered count
dropped 20 → **9**; both duplicate instances (shots 7, 12) confirmed
gone from the ASS output (no `Dialogue` line falls inside either
shot's span); shot 16's complementary caption is unchanged.

Also fixed in the same pass: split-card runs (identical text, two
shots for motion variety) are now judged ONCE over their **combined**
span and given the same decision — shots 30/31 and 62/63 had
individually different coverage (0.33 vs 0.50) that would otherwise
have hidden captions under one half of a heading and shown them under
the other. Both now consistently hidden.

- shot 76's card `لا بطل أسطوري، بل برجل تردد وتألم واختار بشجاعة.`

## P7.10 (2026-07-30) — whole-timeline audit; the real bug was hiding whole shots

User, after the third screening of the same defect class: *"you're far
away from fixing this simple issue! You're supposed to search for EVERY
deviation from the shot plan and anywhere, not only in the examples
mentioned in the last message."* Correct, and the process was the
problem: every fix so far was driven by whichever frame someone
happened to screenshot, so the next screening found another instance
somewhere else. Three rounds of that is a methodology failure, not bad
luck.

**`audit_captions.py` (new)** replaces screenshot-driven debugging. It
reconstructs exactly what `_write_captions` will burn, then walks all
651 narrated words and classifies each one: readable (captioned while
spoken, or displayed on the card that suppressed it), **LOST**,
**DUPLICATED** (a burned line restating the card above it), or
**LEAKED** (burned when not being spoken). Non-zero exit, so it can
gate a render.

First run on the current plan: **69 LOST words in 20 runs, across the
entire film** — an order of magnitude more than the two frames that had
been reported. Root cause, finally: `hidden` was `(shot.start,
shot.end)` for every caption-suppressing typography shot. But a card
holds the frame far longer than its own line takes to say. Every word
of narration that ran on past the card's line, inside the same shot,
was silently deleted. Example: the card `كيف يصنع العسكري ثورة؟`
(spoken 40.06–42.42) holds to 44.54 and swallowed `وماذا يفعل عندما
يقف بين` whole. A second, smaller contributor: P7.8's
`MIN_CLIPPED_WORDS = 3` dropped 1–2-word spans outright — narration
deleted to suppress a symptom that was itself caused by hiding whole
shots.

**Fix — `_card_speech_window(shot, words)`**: a card suppresses the
caption track for exactly the stretch its own words are spoken, located
against the FULL narration (not just within the shot) and then used
whole rather than clipped to the shot. Three properties follow:

* Narration the card does not carry keeps its subtitle → **0 LOST**.
* The card's line is never re-printed as a caption in the neighbouring
  shot, which is what produced the screenshotted duplicates (a card
  holds 5.3 s, its sentence takes 7.7 s, the 2.4 s overflow used to be
  captioned verbatim under/after it) → **0 DUPLICATED**.
* Nothing is lost to the wider window: every word in it is, by
  construction, printed on the card. The audience reads it there, a
  beat before or after it is spoken — the ordinary offset of a pull
  quote. A card whose line is spoken more than `NEAR = 6.0 s` from its
  own shot carries nothing and suppresses nothing.

`MIN_CLIPPED_WORDS` is gone. Stubs are now **merged** into an adjacent
cue instead of dropped (`STUB_WORDS=2`, `JOIN_GAP=0.45 s`,
`MAX_WORDS=14`), so a detached `لأن` or `مستقل؟` joins its neighbour's
line and no word is ever deleted to fix flicker.

Verified across three separate plan revisions (pre-P7.9, retext-era,
and current), each **651/651 words readable, 0 LOST, 0 DUPLICATED,
0 LEAKED, 0 stubs** — and every individually-reported case re-checked:
shots 7 and 12 (the 0:28/0:55 duplicates), the 30/31 and 62/63 split
headings, shot 74 (IMG_5692) and shot 76 (IMG_5693). Shot 76 burned to
pixels: the caption now stops at `ستلتقي برجل حقيقي،` while the card
carries `لا بطل أسطوري، بل برجل تردد وتألم واختار بشجاعة.` —
complementary halves of one sentence, the repetition gone.

Run before any render:

```bash
python audit_captions.py --plan output/shot_plan.json
```

## P7.11 (2026-07-30) — a card must own the frame; the viewer's list was exact

The P7.10 audit passed and the film still had a visible defect, because
the audit was checking the wrong invariant. The user watched the render
against the shot plan and reported the answer directly: *"the following
typography shots caused leakage: 9, 15, 18, 24, 27, 33, 42, 45, 51, 57,
67, 70, 74, 76, 78. Notice that these are not all of the typography
shots. I might suggest to make sure of disappearing the previous text
before imposing the new typography."*

Reproduced mechanically — "which typography shots have any caption on
screen during them" returns `[9, 16, 20, 25, 28, 34, 42, 45, 51, 67, 70,
74, 76, 78]`: nine exact matches, the rest off by one or two from shot
numbering drift between their plan and this one. Same 14–15 shots, and
their suggested cause was right.

**What P7.10 got wrong.** It suppressed captions only for the stretch a
card's OWN line is spoken, and treated a caption of *different* text
under a card as legitimate. It isn't. A full-screen typography card and
a subtitle are two blocks of text competing in one frame; the viewer
reads that as corruption whatever the words say. The invariant is
simpler and stricter than the one that was coded:

> **No caption is ever visible while a typography card is on screen.**

**Why the cards were sitting over unrelated narration.** Measuring
head/tail per card exposed the scale of the original P7.9 problem still
present: cards routinely hold the frame nowhere near their own line —
shot 20's card appears **10.0 s before** its words, shot 16's 4.8 s
before, shot 67's 5.9 s before, shot 51's line finishes *before its card
even starts*. Total 44 s of head + 15 s of tail across 33 cards. Every
one of those seconds is narration the card doesn't carry.

**Fix, in two halves.**

1. *Renderer* — every typography shot now silences the caption track for
   at least its own span, returned as **two separate ranges** (shot span,
   line span) and never merged into one. Merging them was a real bug
   found in testing: a displaced card 10 s from its line produced a
   single 15 s interval that silenced everything in between, including
   unrelated shots. `card_hides_captions=False` no longer exempts a card
   from owning its frame; it now only means "don't extend the silence to
   the card's line elsewhere".
2. *Plan* — since a card now silences everything under it, every second
   it holds beyond its own line costs a readable clause. So the trim in
   `sync_typography_to_speech` became far more aggressive: it shrinks a
   card to the *overlap* with its line (not just when the line is wholly
   inside), and a new **Case 1b** shrinks a genuinely displaced card to
   its minimum readable hold, handing the freed seconds to a
   neighbouring image shot where captions run normally. Neighbours may
   absorb past `HARD_CAPS` by `CAP_SLACK = 1.5 s`, and absorb
   *partially* when they cannot take it all — all-or-nothing was
   rejecting fixes that missed the ceiling by fractions (shot 51 needed
   9.69 s against a 9.5 s limit and lost its whole clause for it).

**Result on the reference plan** — cards trimmed 8 → **20**:

| | before P7.11 | after |
|---|---|---|
| typography shots with a caption over them | **14** | **0** |
| DUPLICATED | 0 | 0 |
| LEAKED | 0 | 0 |
| words heard but not readable | 0\* | 38 |
| longest shot | 7.87 s | 9.50 s |

\* P7.10 scored 0 only because it counted a caption-under-a-card as
"readable"; that is the defect being fixed here.

`CAP_SLACK` was tuned against this trade-off directly — 0.0 → 66 lost /

## P7.14 (2026-07-30) — time-limited overlay: the structural fix, LOST 21 → 14

Option 2 above, implemented. Since P7.11 the pipeline had been forced to
choose per card between two bad outcomes — silence the narration a card
doesn't carry (words LOST), or let a subtitle share the frame with it
(leakage). That dilemma only exists because a card was assumed to own
its shot for the shot's whole length. In `typography-over-image` mode it
doesn't have to: the "card" is text composited over footage, so it can
appear only while its own line is spoken and let the rest of the shot
play as ordinary captioned footage.

FFmpeg's `overlay` filter takes `enable='between(t,a,b)'`, and the
renderer was already emitting timed `enable` clauses for the
word-by-word reveal — so the mechanism was there, just applied to the
wrong axis. `_overlay_png_on_clip` and `_overlay_steps_on_clip` gained a
`window` parameter; the reveal now builds up *inside* that window rather
than across the whole clip.

**Verified in a real encode, not assumed** — a window of (2.0, 4.0) on a
6 s clip: overlay hidden at t=1 s (RGB 29,58,87 = bare background),
visible at t=3 s (253,238,198), hidden again at t=5 s. Reveal path
likewise: 0 lit pixels at 1 s, 1620 at 2.2 s, 6420 at 3.5 s, 0 at 5 s.

The window is computed by `_overlay_visible_window` and **recorded by
the render loop itself**, then handed to `_write_captions` — never
re-derived. The over-image path silently falls back to a static card
when there is no prior real image to sit on, so a caption track that
re-derived the window could disagree with what was actually drawn;
passing the recorded dict makes that impossible.

Result on the reference plan: **28 of 33 cards** now draw as
time-limited overlays. `LOST 21 → 14`, with `DUPLICATED 0, LEAKED 0,
CAPTION-OVER-CARD 0` — the trade-off is gone, not balanced.

Also corrected in the audit: a time-limited card is only *visible* for
its window, but while visible it displays its **entire line**, so every
word of that line has been read even if spoken after the text clears.
Readability is credited across the whole line; visibility (the leak and
duplication checks) only across the window. Scoring visibility for both
briefly reported 82 LOST — an artefact of the model, not the render.

**Confirmed in the user's own render** (2026-07-30), which is the test
that matters — shot 42, one shot, one image, two moments: at 201.5 s the
pull quote "النظام الجديد حمل فساداً من نوع آخر، ومصالح شخصية تعترض طريق
الإصلاح الحقيقي." is on screen with no caption; at 204.2 s the quote has
cleared, the same illustration plays on, and the caption "كانت هذه فترة
من الصراع النفسي الحاد لضابط شاب يؤمن بقوة التغيير،" is readable
underneath. Their audit run reproduced this repo's numbers exactly
(LOST 14, everything else 0).

**Residual: 14 words (2.2 %) in 4 runs**, all under *displaced* cards
that Case 1b has already shrunk to the 1.6 s readability floor — there
is no room left to split, and shrinking further would make the card
unreadable. Measured directly: disabling Case 1b to leave room made it
*worse* (18 LOST), so the current combination is the floor for this

## P7.15 (2026-07-30) — alignment mapped by POSITION, not content

A fresh total solution came back worse than the render-only cut it
replaced: *"the deterioration begins after ~1:12 where there are
noticeable differences between narration and captions. Repetition is
also noted."*  A new plan making things worse points upstream of the
planner, and it did — to `align._map_tokens_to_asr`.

**The bug.**  That function paired each script token with an ASR word
**by position**, and when the counts differed it stretched one onto the
other *proportionally*.  Its own docstring called it "a much simpler
heuristic than dynamic-programming alignment".  The flaw is that ASR
errors are LOCAL — a dropped word here, two merged there — while
proportional mapping is GLOBAL.  Measured on a synthetic 200-token
script, a single 3-word deletion at index 100 put **every** token out by
up to 2.00 s, including tokens *before* the deletion (w50 drifted
−1.00 s, w99 −2.00 s).  That is precisely "captions drift out of sync
partway through, and it gets worse".

**The fix.**  Anchor on content, interpolate only inside gaps: normalise
both streams, take `difflib`'s matching blocks as anchors (those tokens
get their ASR word's timing verbatim), spread unmatched runs evenly
between the surrounding anchors, extrapolate at the ends, then enforce
monotonicity.  An ASR error is now confined to its own gap.

|---|---|---|---|---|

| 5 scattered drops | 0.64 s | 0.13 s | **0.09 s** | **0.001 s** |
| 8 insertions | 0.64 s | 0.23 s | **0.00 s** | **0.000 s** |
| 4 drops + 4 inserts | 1.28 s | 0.34 s | **0.09 s** | **0.000 s** |
| 20 drops + 20 inserts | 0.64 s | 0.34 s | **0.09 s** | **0.003 s** |
