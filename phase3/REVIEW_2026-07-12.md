## 1. Cost anatomy (issue 1)

Measured/derived from the current pipeline for one total-solution run
(96 shots → 57 image shots):

| Stage | Calls | Est. cost |
|---|---|---|
| Vision scoring (Haiku, 1 call per candidate) | 57 shots × ~7 candidates ≈ **400 calls** (~1.1 k input tok each: image ~640 + rubric ~500) | **$0.55–0.70** |
| Shot planner (Sonnet 4.6, `max_tokens=24000`) | 1 call, ~15 k output tokens for 96 shots | $0.25–0.35 |
| Photo-bank captioning (Haiku, cached after first run) | ~1 per bank photo | ~$0.02 |
| Photo-bank assignment (Sonnet) | 1 | ~$0.05 |
| **Total** | | **≈ $0.90–1.10** ✓ matches observation |

Vision scoring dominates. Its cost structure is *pure waste* in four ways:

1. **The 500-token rubric is re-sent 400 times** (~200 k redundant input
   tokens/run) because each candidate gets its own API call.
2. **Every candidate from every source is scored**, even when the first
   Wikimedia result already scored 9/9 era 3 — Pexels candidates are then
   fetched, downloaded, and scored for nothing.
3. **Duplicates are scored twice**: a Wikipedia lead image is very often the
   same file Commons already returned; there is no cross-source URL/dHash
   dedupe before scoring.
4. **The cache is ephemeral on Colab**: `~/.cache/lamahat/images` dies with
   the VM, so every fresh session re-downloads and re-scores everything.
   Re-runs that should be free cost full price.

Also structural: prebuild runs the full waterfall for **portrait shots that
the character pool will resolve anyway** (9 pool hits in the sample render —
each still paid for fetched-and-scored web candidates it never used), and for
photo-bank-assigned shots unless `--photo-bank-only`.

### Fix plan (ranked by savings)

| Fix | Change | Est. saving |
|---|---|---|
| **C1. Batch vision per shot** | One Haiku call scoring *all* of a shot's candidates as numbered images (the API takes multi-image content blocks); rubric sent once per shot → 57 calls instead of 400 | ~45 % of vision cost |
| **C2. Staged waterfall + early exit** | Query Wikimedia+Wikipedia first, score, and **skip Pexels entirely** when ≥2 candidates pass threshold with era ≥ 2 (for period shots Pexels should be skipped anyway — see §4) | ~30 % of vision cost + all wasted Pexels downloads |
| **C3. Skip covered shots at prebuild** | Character-subject portrait shots (pool exists) and bank-assigned shots don't need the web waterfall; make skipping the default (`--fetch-covered` to opt back in) | ~15–20 % |
| **C4. Cross-source dedupe before scoring** | dHash/URL match across the pooled candidates; score each distinct image once | ~10 % |
| **C5. Persist the cache on Colab** | `LAMAHAT_CACHE=/content/drive/MyDrive/Lamahat/cache` in the notebook settings cell (the code already takes `--cache-dir`); additionally key vision scores by (content-hash, query) so a re-plan with identical queries re-uses scores | makes re-runs ≈ free |
| C6. Trim planner output | Drop `note`/rationale from the emitted JSON schema (keep it in a debug sidecar); ~30 % fewer output tokens on the plan call | ~$0.08 |

C1+C2+C3 alone take a fresh run to **≈ $0.30–0.40**; C5 makes iteration runs
nearly free. None of these change *what* renders — only how much is fetched
and how scoring is billed.

## 2. Framing / zoom (issue 2) — and the resolution standard

### What actually happens to a 2560×1706 (3:2) "full-screen" image

The notebook renders with `--parallax`, so every image shot goes through
`motion_parallax.render_parallax_clip`:

1. **Aspect cover-crop** — `_fit_to_frame` (mismatch 0.28) classifies 3:2 as
   "cover" and center-crops it to 16:9: **15.6 % of the height is cut**
   (top+bottom), with no knowledge of where the subject is.
2. **Fixed 1.18 buffer** — the image is fitted to a 2266×1274 buffer, but the
   output frame is always the *central 1920×1080* of that buffer: another
   **15.3 % of each axis is never visible**, even for a static camera. The
   margin exists so camera displacement never reveals an edge, but it is
   sized for the *worst case* (amp_px 70) while portraits/archive shots move
   at amp 36–42.
3. **Dolly zoom** — up to a further 2–6 %.

Net: **height visible ≈ 1080/1510 ≈ 71 %**, width ≈ 85 %; you see roughly
**60 % of the source pixels**, cropped blind. That is precisely "considerable
parts of them are not visible". (The non-parallax `zoompan` path is much
gentler — full frame at zoom 1.0, max −8 to −20 % at peak zoom — the
regression came with parallax becoming the default look.)

### Recommendation — where each crop should live

- **R1. Motion-proportional buffer.** Replace the fixed `_BUFFER = 1.18` with
  `buffer = 1 + 2·(amp_px + zoom_margin_px)/out_w` computed per shot
  (≈ 1.06–1.08 at current amplitudes). Straight recovery of ~9 % on each
  axis for every parallax shot; zero look change (the margin was never seen).
- **R2. Move the aspect crop to conditioning, make it deliberate.** The blind
  center-crop in `_fit_to_frame` is the biggest and least excusable loss.
  `condition_assets.py` already classifies cover vs contain — it should also
  **emit the 16:9 crop itself** (face/saliency-aware placement; the deferred
  P2.3 saliency work belongs *here*, not in the renderer), writing a
  `.cond.jpg` that is already 16:9. The reviewer then sees in the dossier
  exactly the framing that will render — today the dossier shows the whole
  image and the renderer silently cuts a third of it.
- **R3. The standard.** With R1+R2 in place the answer to "what is the most
  suitable full-screen resolution" is:

  | Class | Standard | Why |
  |---|---|---|
  | Full-screen (cover) | **2560×1440, 16:9** | 1920 output × ~1.07 buffer × 1.08 max zoom ≈ 2220 px needed; 2560 keeps one sharpening margin. A 16:9 source suffers **zero** aspect crop |
  | Contained portrait | native aspect, **height ≥ 1600** | unchanged (`contain_floor`) — portraits are never cropped |

  2560×1706 (3:2) is the wrong target *because of its aspect*, not its pixel
  count — every 3:2 source donates 15.6 % of its height to a blind crop.
  Update `condition_assets.py --target-cover` semantics accordingly
  (target becomes a 2560×1440 canvas, not a long-edge).
- R4 (optional): expose `--parallax-amp-scale` so the curator can trade
  motion for visibility globally on archive-heavy cuts.

## 3. Review dossier (issue 3) — top-3 policy

Current behaviour, Colab route (the one actually used):

- `prebuild_assets.py::_process_shot` copies **every downloaded candidate**
  into the shot folder — typically 7–9 files × 57 shots ≈ 400–500 images —
  including sub-threshold rejects ("irrelevant ones") and near-identical
  Wikipedia/Wikimedia twins ("repeated images"). Candidates are written in
  *source order*, not ranked order.
- `condition_assets.py` then adds a `.cond.jpg` (2560-long-edge, JPEG q95,
  ~1.5–3 MB) beside each winner.
- `slim_review_dir` exists but **only `build_total_solution` (Streamlit)
  calls it** — the notebook zips the raw dossier (cell 17), so the user
  reviews and downloads the unslimmed tree.

### Fix plan

- **D1. Cap at prebuild, don't slim after.** In `_process_shot`: rank with
  `vision.rank_candidates`, apply `passes_threshold`, and **copy only the
  top-3 keepers** (plus the bank photo / winner, always). Keep *metadata* for
  everything in `candidates.json` (with a `not_copied: true` flag) so nothing
  is hidden from the curator — only bytes are saved. `--dossier-keep N`
  (default 3) for control. This also composes with C4 (dedupe): the three
  images kept are three *distinct* images.
- **D2. Never copy sub-threshold candidates.** A subject=0 clip-art candidate
  has no review value; its metadata line in `context.txt` is enough.
- **D3. Notebook slims before zipping.** Add
  `slim_review_dir(REVIEW_DIR, mode="top", keep_n=3)` to cell 17 for dossiers
  produced before D1 lands.
- **Constraint to respect:** `--backdrop-rotate` and the dedupe-swap both
  consume *ranked alternates from the dossier* — top-3 is exactly enough for
  them; the current `slim_mode="chosen"` default (Streamlit) actually
  **breaks** backdrop rotation on a re-render from a slimmed dossier. Change
  the Streamlit default to `mode="top", keep_n=3` too.

Expected size: ≈ 57 × (3 + 1 cond) ≈ 230 files, roughly **3–5× smaller**,
and every image in the dossier is one a curator might actually pick.

## 4. Era (issue 4) — from soft demotion to a first-class contract

Evidence from this cut:

- **Pexels won 26 / 57 image shots (46 %)** — for a 1904–1936 memoir, nearly
  half the imagery is modern stock by construction (Pexels queries are even
  *stripped* of period tokens, guaranteeing modern results, which the tone
  pass then disguises).
- Frame at t≈35 s: a **1950s Cairo street demonstration** (megaphone,
  mid-century dress, tank-emblem banner) inside the Ottoman-officer
  narrative — wrong decade, wrong country.
- Frame at t≈12 s: sepia-toned **modern Istanbul skyline with present-day
  cars** along the waterfront as the establishing shot.
- **Photo bank won 0 shots** in this render — the mechanism built precisely
  to fix era (Path C) is not landing assignments.
- The era axis exists only as a per-candidate vision inference from the
  *query text* ("if the query implies a period…"), and only *demotes*.
  When every candidate is anachronistic, the least-bad still renders.

For a documentary this is the wrong default: **a period-false image is worse
than no image.** The system already has an honest fallback (typography
cards); it should use it.

### Fix plan

- **E1. Era in the plan.** Add `era: str` to the `Shot` dataclass (e.g.
  `"1900s–1910s Ottoman Mesopotamia"`, or `"timeless"` for texture/landscape
  b-roll where modern stock is legitimate). One planner-prompt rule; Sonnet
  knows the book's chronology — today that knowledge is thrown away and
  Haiku re-guesses it per image from six words of query.
- **E2. Era hard gate for period shots.** For shots whose `era` is not
  `timeless`: candidates scoring era ≤ 1 are **excluded**, and if nothing
  passes, render the §7.7-style **Arabic typography card** (planner's key
  phrase for that beat) instead of the least-bad anachronism. Config
  `era_strict` (default **on**); demotion-only remains available for
  b-roll. This is the direct implementation of "the documentary should
  always take care of the era".
- **E3. Don't ask Pexels for the past.** For period shots, Pexels leaves the
  waterfall entirely (composes with C2's staged fetch); it stays for
  `timeless` b-roll only. Tone conditioning then goes back to being a
  polish, not a disguise.
- **E4. Vision gets the era explicitly.** Pass `Shot.era` into the rubric
  instead of "if the query implies a period" — cheaper prompt, better
  signal, and it closes the rubric blind spots the ledger already logged
  (the 1815 Italian ledger, the Baroque portrait).
- **E5. Find out why the bank landed 0 assignments** in this run (captions
  quality? assignment prompt? `PHOTO_BANK_MAX_USES=1`?) — one diagnostic
  prebuild with `--verbose` and the assignment debug JSON in the dossier.

## 6. Other findings (the "not hidden from a professional" list)

1. **Typography density 41 %** (39 text shots / 96) — above the 35 % prompt
   ceiling that the 43-shot plan respected; the film also **closes on three
   consecutive typography cards** (shots 94–96). A documentary should end on
   an image or the title card. Worth one planner-prompt rule: never more
   than one typography shot in the final 20 s; re-assert the 35 % cap for
   large plans.
2. **96 shots ≈ 8 min of timeline** — the master plan targets 3–5 min. Not a
   Phase 3 defect (narration length is set upstream), but the shot count
   drives both planner cost and prebuild cost linearly; worth checking the
   ElevenLabs narration length before the next full run.
3. **Depth estimated at render time for rotated backdrops** — the log shows
   `no cached depth for shot_070_bgrot.png; estimating in-memory` for every
   `--backdrop-rotate` alternate. Once D1 lands (top-3 kept), prebuild can
   pre-warm depth for all three keepers cheaply.
4. **Adaptive scrim did not engage on a busy frame** — the word-reveal at
   t≈35 s sits over a dense crowd with no plate; the auto heuristic
   (brightness-weighted) misses busy-but-mid-brightness backdrops. Consider
   adding a local-contrast term to the busy test in the scrim sampler.
5. **`slim_mode="chosen"` breaks re-render features** — a dossier slimmed to
   winners only has no alternates for `--backdrop-rotate` or dedupe swaps on
   the render-only route (§3, constraint).
6. **Duplicate resolve log lines** (shots 87, 89, 91, 93 re-resolved for each
   overlay card in a run) — cosmetic, but they make the log read as if shots
   render twice; worth a `debug`-level demotion.
7. **Doc drift**: `PHASE3.md` §0 still says notebooks pin `BRANCH` for the
   P-batches and lists "merge `claude/phase3-review-plan-8sbeue`" as next —
   that merge has happened (this tree is `main`-derived); CLAUDE.md's
   "Immediate Next Steps" has the same stale item.
